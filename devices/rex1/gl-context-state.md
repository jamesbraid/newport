# REX1 context state the IRIX 6.2 GL sets: buffers, write mask and clip

What the OpenGL library for the Indigo Entry board puts in `AUX1`, `AUX2`, `RWMASK`, the screen mask and the window offset around its draws, and what each is expected to do. The colour and shading side is on [shaded drawing](shaded-drawing.md), lines on [true lines](true-lines.md), the register list in [registers.md](registers.md). Grades, tags and the objects read are the same as on the shaded-drawing page (`libGLcore.so` of `usr/gfx/arch/IP20LG1MC` in IRIX 6.2, read as MIPS disassembly; the ide sources under `stand/arcs/ide/fforward/graphics/LIGHT/`); the Entry-run trace is a decoded log of `ivview` on the emulated Entry model and shows what the guest sends, not what a chip does.

## Coordinates, the window offset and what a clear leaves behind

The GL stores every x and y with the high bit of a float's magic constant still on: the trace's clear is `XSTARTI` 0x1800, `YSTARTI` 0x19c3, `XENDI` 0x19cb, `YENDI` 0x1800. The chip keeps 12 bits of each (the ide test mask is 0xfff), so these are 0x800, 0x9c3, 0x9cb and 0x800: the window-relative coordinate biased by 0x800, which `XYWIN` (0x003e003c in the trace: x 62, y 60, no bias) turns back into screen coordinates. The clear then covers screen x 62..521 and y 60..511, exactly the 460 by 452 GL area at (62, 60), with `YSTARTI` the larger row and `YENDI` the smaller: the engine runs from `YSTARTI` toward `YENDI`, as the [REX1 page](README.md#y-origin) says. **Established** for the stores **[binary]** (`__glSetDrawBuffer` 0x0dab79f4, the RGB clear at 0x0dab7c70), **inferred** for the offset arithmetic (`XYWIN` page note).

The clear order is `COLORBLUE`, `XSTARTI`, `YSTARTI`, `XENDI`, `YENDI`, `COLORRED`, `COLORGREEN`, then `COMMAND` GO with the word. After the clear the guest's context swap reads the draw state back, which the trace records: `XSTART` 0x04000000 and `YSTART` 0x04e18000 (the *start* of the fill, 0x800 and 0x9c3 shifted left 15: a block fill leaves the start registers where they were, it does not walk them to the end), `XENDF` 0x004e5800 and `YENDF` 0x00400000 (the end values shifted left 11, so they read back as stored) and `COLORRED` 0 (the 20-bit colour of 0x45c00000). This is the model's own read-back (not a chip), so it is a consistency check, not evidence; the same read-backs follow from the [ide register test](registers.md) rules.

## `AUX1` and the double buffer

The library chooses `AUX1` in one routine (0x0daad950 to 0x0daad9f8, between `__glrexim_FastColor3ubv` and `__glRexAllocAccum`) and stores it both in the context and in the chip. **[binary]** The base is 0x202 for a single-buffered window (and for the overlay), 0x222 for a double-buffered one. For a double-buffered window the draw-buffer state adds the destination bits:

| `glDrawBuffer` | buffers not swapped | buffers swapped | result bits |
|---|---|---|---|
| `GL_FRONT` | `DBLDST0` | `DBLDST1`, `DBLSRC` | 0x226 or 0x23a |
| `GL_BACK` | `DBLDST1`, `DBLSRC` | `DBLDST0` | 0x23a or 0x226 |
| `GL_FRONT_AND_BACK` | both destination bits | both | 0x22e |
| anything else | none | none | 0x222 |

The "swapped" state is a context word that flips at every buffer swap; so with the default `GL_BACK` the words alternate 0x23a, 0x226 from frame to frame, as the trace shows (`AUX1` 0x23a at the first clear, then both values alternating). The read routines (`__glRexRenderBitmap`, which reads one pixel with the command word 3) use 0x222 or 0x232, that is `DBLSRC` alone picks the buffer to read. **Established** for the words and their selection; the bit names are the header's (`DBLDST0` 0x4, `DBLDST1` 0x8, `DBLSRC` 0x10, `DOUBLEBUF` 0x20).

**Which nibble.** The software fixes only a naming: `DBLDST0` and `DBLDST1` write buffer 0 and buffer 1, `DBLSRC` set reads buffer 1, and a swap changes both the library's `AUX1` and the mode word of the window's display ID. In the trace's swap the mode word of display ID 1 goes from 0x030f to 0x030d (bit 1 cleared) at the moment `AUX1` goes to 0x23a, having been 0x226 for the frame just drawn; the frame just drawn is therefore the one displayed, which makes bit 1 of the mode word the number of the buffer that is **shown** (1 shows buffer 1, 0 shows buffer 0). **Inferred**, from one swap and the library's own alternation; the first frame's initial mode word is not in the trace. Which physical nibble of the 8-bit pixel is buffer 0 and which is buffer 1 is **unknown**: nothing shipped depends on it, because the chip writes both and the video side reads one. A model needs only the pairing: draws with `DBLDST0` go to the nibble that mode-word bit 1 = 0 displays, `DBLDST1` the other. Taking buffer 0 as the low nibble is an arbitrary choice and an approximation.

**Pixel and mask width.** With `DOUBLEBUF` set and one destination bit, the pixel and plane mask are four-bit values in window space: the library gives `RWMASK` 0xf for both buffers, and the X server's tile fill, which writes `AUX1` 0x28 (one destination bit), shifts its eight-bit plane mask right by four, while with 0x2c (both bits) it does not ([tile fill](tile-fill.md)). **Inferred** that the chip steers the low four bits of the pixel into the chosen nibble, and both nibbles for both bits. This holds for shaded rows, clears and points alike, since the library uses the same `AUX1` for all of them.

## `RWMASK`

`RWMASK` (0x78) is stored as follows. **[binary]** Once at context set-up: 0xff (together with `AWEIGHT` and `CONFIGMODE`). After every draw-buffer change (`__glSetDrawBuffer` tail, the store at 0x0dab7dc8, and its colour-index twin at 0x0daac238): the context's full-width mask (15 for the 4-bit window, 255 for the 8-bit one; the trace's pixel-plane context shows 0xf and the overlay 3) when the draw buffer is not `GL_NONE`, and **0 when it is `GL_NONE`**. `glColorMask` and `glIndexMask` only store the mask in the context and mark it dirty; no `RWMASK` store was found on that path.

So the one case where the library depends on `RWMASK` doing something is `glDrawBuffer(GL_NONE)`: a draw with the mask at 0 must leave the planes alone. That is a **software expectation** that `RWMASK` gates the library's own draws (the clear 0x3000c329, the shaded and flat rows, points, lines), whose command words carry the logic operation in bits 31:28 (3 = replace). **Inferred**, because the library could also have avoided the draw in software; but the guest stores `RWMASK` immediately before every phase (the trace has it before the clear and before each batch of slope stores), which a mask that did nothing would not need.

It must not gate the paths that work with `RWMASK` at 0: the X server's own fills use command words with an empty logic-operation nibble and take their mask from `XSTATE` 23:16, and its host-data commands (tile fill, PutImage, GetImage) run with `RWMASK` 0 ([colour-map install](../../platforms/lg1/colormap-install.md#4-rwmask), [tile fill](tile-fill.md)). One rule that fits every shipped writer: **a draw whose command word has a non-zero logic-operation nibble and no `COLORAUX` (bit 21) is masked by `RWMASK` in window space; draws with an empty nibble use `XSTATE`, and `COLORAUX` draws are not masked by `RWMASK`.** The kernel's and the PROM's fills (nibble 3, `RWMASK` 0xff) are consistent with it. This is an **inference** from the union of the guests, graded as an approximation for a model, with no discriminating hardware evidence; the model should store `RWMASK` whatever it does with it.

## `SMASK1` and `AUX2`

`AUX2` (0x47a8) for a GL context is the plane group in bits 31:29 (1 pixel planes, 2 overlay planes) and 0xff1 below. **[binary]** The 6.2 `libGLcore.so` itself never stores `AUX2` or either `SMASK1` register (no store to `AUX2`'s offset anywhere in the library, none to the `SMASK1` offsets in any of the `Rex` routines), so a GL context's values come from the kernel's context switch. 0xff1 is the value both the kernel (the context default built at `light.o` +0xcb8) and the X server (`rexValidateClip` +0x58, 0x5e4be0b8 in the 6.2 object) store for the low bits of a window context. The shipped header names the fields: bits 3:0 `SMASK0` to `SMASK3` (enables), bits 7:4 `SMASK0_IN` to `SMASK3_IN` (polarity), bits 23:8 the four `CIDMATCH` nibbles. 0xff1 therefore reads: screen mask 0 enabled with inside polarity (bits 0 and 4), the other three masks disabled with inside polarity set (bits 7:5), and the first CID match nibble 0xf (bits 11:8). The X server's batches use 0xf11 (bits 0, 4 and 11:8 only). **Inferred** from the names, since no code states the effect; the enable and polarity pairing by number is the header's, and the header counts the masks from 0 while the registers are `SMASK1X`/`SMASK1Y` to `SMASK4X`/`SMASK4Y`, so enable bit 0 is taken to belong to the first register pair.

`SMASK1X` and `SMASK1Y` hold the window rectangle: in the trace 0x0209003e and 0x01ff003c, that is maximum x 521 (bits 25:16) and minimum x 62 (9:0), maximum y 511 and minimum y 60, inclusive, in screen coordinates (not biased by `XYWIN`), which is the GL area itself. The kernel's `lightComputeSmask1` computes the window's visible rectangle clipped to the screen and stores it there ([REX1 page](README.md#drawing-model)); on a context swap the other three masks are written 0 and `SMASK1` is written twice, once with a placeholder 1 by 1 rectangle (0x003d003d, 0x003c003c) while the swap is in progress and then the window rectangle. So **`SMASK1` is the clip for every draw of the context**, the clear and the shaded rows included: the GL's own clipping is to the window and the scissor (`__glRexScissorLine`), and no clip against overlapping windows was found in the clear, span, line or triangle-row routines read. **Inferred** (names, the kernel's computation and the absence of another clip; nothing in the trace can show it, because the rows stay inside the rectangle).

What a model does: enable `SMASK1` when `AUX2` bit 0 is set, treat bit 4 as inside (draw only pixels with min <= coordinate <= max on both axes, after the `XYWIN` offset), ignore the other three masks while their enable bits are clear, and store the CID nibbles without effect. Discriminating checks: with `AUX2` low bits 0x11 and `SMASK1X`/`Y` set to a 4 by 4 rectangle, a block fill larger than it changes only those pixels; with bit 0 clear it changes all of them.
