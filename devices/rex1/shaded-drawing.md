# REX1 shaded drawing: what the IRIX 6.2 GL sends for colour, dither and shaded spans

How the OpenGL library for the Indigo Entry board colours pixels: the command bits, the colour registers, the slope registers and the dither flag. The register list is in [registers.md](registers.md), the engine model on the [REX1 page](README.md), the buffer, mask and clip state the same library sets up on [GL context state](gl-context-state.md), and lines on [true lines](true-lines.md).

Grades follow [AGENTS.md](../../AGENTS.md). Tags: **[binary]** read in a shipped object with its address; **[source]** the IRIX source tree, by path; **[hdr]** a name from the shipped header `sys/lg1hw.h` (6.2 copy, revision 1.28; the names the Linux Newport header also carries are public); **[inferred]** says what it rests on. Everything here is what *software expects*: no register was measured on a board, and the library's own arithmetic is the only evidence for what the chip does with the values it is given.

Objects read, all from the IRIX 6.2 install media (`eoe.sw.gfx`, subsystem for the IP20 and the LG1MC graphics arch; hashes in [irix-files.md](../../references/irix-files.md)): `libGLcore.so` of `usr/gfx/arch/IP20LG1MC` (the OpenGL renderer; its exported `__glRex*` symbols name every routine below) and, for the shared constants only, `libgl.so` of the same directory. The IRIX source files cited are the ide diagnostics in `stand/arcs/ide/fforward/graphics/LIGHT/` (`minigl.c`, `rex.c`, `vram.c`, `rexpatterns.c`), which drive the same chip through the same registers. The dynamic symbol tables name the routines; the functions were read from first to last instruction by hand from a MIPS disassembly (no decompiler), so every reading is **established** for what the code stores and **inferred** for what the chip does with it. The Entry-run trace quoted for the observed words is a decoded log of `ivview` on the emulated Entry model (model output, not hardware evidence; it shows what the guest sends, which is all it is used for).

## What the guest sends for one shaded triangle row

`__glRexFillRGBGZSubTriangle` walks a triangle scan line by scan line; it has seven siblings (colour index or RGB, flat or smooth, with or without the depth mask; `__glRexFillRGBSubTriangle`, `__glRexFillCIGZSubTriangle` and the rest), and only this one was read from first to last instruction. **[binary]** Per row it stores, in this order: `XSTARTI` (0x0c) the left pixel, `XENDI` (0x84) the right pixel (the right edge minus one, an inclusive end), `YSTARTI` (0x1c) the row, `COLORRED`, `COLORGREEN`, `COLORBLUE` (0x3c, 0x44, 0x4c) the colour at the left pixel, `COMMAND` GO (0x800) with 0, `COMMAND` (0x000) with the row command, and then the depth routine writes the per-pixel mask word(s) to `ZPATTERN` GO (0x860). The slope registers (`SLOPERED`, `SLOPEGREEN`, `SLOPEBLUE`, 0x50, 0x54, 0x58) are written once per triangle by `__glRexComputeSlopes`, not per row. Host code, not the chip, steps the left edge from row to row (the left colour of the next row is computed on the host); the chip supplies only the step across the row. The Entry-run trace shows exactly this order for 5041 rows in one frame (the word 0x3212c5b1 is what `__glRexPickTriangleProcs` builds for a shaded, depth-masked RGB row, section 1), and about ten percent of rows with no mask store: the depth routine writes no word when every pixel of the row failed.

## 1. The command bits

The bits 14, 15, 17, 20 and 25 are all named in the shipped header and all built by `__glRexPickTriangleProcs` (0x0dab030c) and the span, point, line and clear routines. **[binary]**

| Bit | Value | Header name | Set when (6.2 GL) | Reading |
|---|---|---|---|---|
| 14 | 0x4000 | `RGBMODECMD` | every draw in RGB mode: flat spans 0x30004121, points 0x30004001, clears 0x30004329, triangle rows 0x32004121 | the colour comes from the three colour registers, not the single index in `COLORRED`. **Established** for the names and use; the effect is **inferred** and agrees with the ide VRAM test, which sets `RGBMODECMD`, loads three integer colours and expects a block fill to leave a pixel whose three fields are those channels' top bits ([source] `vram.c`) |
| 15 | 0x8000 | `DITHER` | added whenever `glEnable(GL_DITHER)` is on (the default; `__glim_Enable` sets bit 3 of the context's enable word for it), RGB and colour-index alike: the overlay clear is 0x30008329 (bit 15 alone, an index colour), the pixel-plane clear 0x3000c329 (bits 15 and 14) | position-dependent rounding of the colour to the pixel; see section 2. When it is off the library adds its own rounding offset instead. **Established** for the use, **inferred** for the effect |
| 17 | 0x20000 | `SHADE` | the colour changes across the draw: shaded spans 0x30024121 (flat CI 0x30000121), shaded pattern rows `…5b1`, shaded triangle rows | the three slope registers advance the colour from pixel to pixel; see section 3. The ide `_span` sets it, and `_polygon` loads the three slopes before each `_span` call; the ide `_line` does not set it ([source] `minigl.c`) |
| 20 | 0x100000 | `SHADECONTINUE` | only together with `SHADE` on rows drawn from `ZPATTERN` words (`…5b1`): shaded stippled spans and shaded depth-masked triangle rows | the row is fed as several 32-pixel pieces (one `ZPATTERN` word each; a span wider than 32 pixels takes two or more), and the colour continues from the end of one piece into the next instead of restarting. **Inferred** (name; the flag is set exactly where several pieces can follow, never on a flat row; the alternative reading, carry across rows, is not distinguished) |
| 25 | 0x2000000 | `LRQPOLY` | every triangle row command of the OpenGL library (flat and shaded, CI and RGB, masked or not: `__glRexPickTriangleProcs`); in the IRIS GL library only the plain span word 0x32040121 that `gl_init_wstate` (`libgl.so` 0x0f0a367c) stores, together with `INITFRAC`; spans, points, lines and clears of the OpenGL library leave it clear, and so do the IRIS GL stippled span (0x300405a1), block fill (0x30040129), point (0x30040001), line stipple (0x30040801) and image word (0x30240089) | **Effect unknown: no shipped software depends on it.** The name reads as a left/right quad polygon flag. The ide `_span` issues the same span shape (`QUADMODE`, `STOPONX`, `SHADE`, `DRAW`) without it, `_polygon` loops that span for the shaded-polygon and colour-span screens of `rexpatterns.c`, and the library's own spans stay valid with it clear, so the pixels a span writes do not need it (**software expectation**). Routes tried: ide `minigl.c`, `rex.c`, `vram.c`, `rexpatterns.c`, `cid.c`; the kernel, both PROMs and the 5.3 and 6.2 `lg1mc.so` (no command word with bit 25 found among the words on the REX1 page and the immediates); the OpenGL and IRIS GL libraries (the uses above); the public header only names it. A model draws the row as if the bit were clear and need not log it |

Other bits the same routines build, for completeness: the logic operation in 31:28 comes from the GL logic-op state when it is enabled and is 3 (replace) otherwise (read in the colour-index span, triangle-row and line builders and in the point builder, which applies it to RGB points too; the RGB span, triangle-row and line builders and the clears always use 3); `0x121` (`QUADMODE`, `STOPONX`, `DRAW`) is the span; `0x490` (`ENZPATTERN`, `XYCONTINUE`, `LENGTH32`) turns it into a mask-driven row, 0x5b1 in all; `0x2000` (`LSCONTINUE`), `0x800` and `0x1000` (`ENLSPATTERN`, `LSADVLAST`) are the line stipple bits ([true lines](true-lines.md)). The word seen in the trace, 0x3212c5b1, is the triangle word with a depth mask and shading: 0x32004121 (`LRQPOLY`, `RGBMODECMD`, `STOPONX`, `QUADMODE`, `DRAW`) with `SHADE` (0x20000), `DITHER` (0x8000), `ENZPATTERN` | `XYCONTINUE` | `LENGTH32` (0x490) and `SHADECONTINUE` (0x100000), reproduced bit for bit by reading the builder.

0x8000 alone clearing the overlay and 0xc000 the pixel planes is therefore not a plane selector: both clears are the block fill 0x329 with the dither bit the GL always adds, and the plane group is `AUX2` bits 31:29 (2 for the overlay, 1 for the pixel planes, [plane groups](../../platforms/lg1/desktop-and-overlays.md#plane-groups)). Bit 14 is set in the second because that window is RGB. With the GL dither state off the same code issues 0x329 and 0x4329.

## 2. Colour to pixel: truncation or dither

**Pixel layouts.** The 8-bit TrueColor window is red 7:5, blue 4:3, green 2:0 ([source] `vram.c`: from the colour byte the test builds red as `0x24 *` bits 7:5, green as `0x24 *` bits 2:0 and blue as `0x55 *` bits 4:3, loads them through the three integer colour registers and expects a block fill in RGB mode to read back that byte). The 4-bit double-buffered window is red 3, green 2:1, blue 0: the colour map the X server loads for it has entry n red = bit 3, green = bits 2:1, blue = bit 0 ([colour-map install](../../platforms/lg1/colormap-install.md)). Both are the top bits of each channel; **inferred** that the chip keeps the top n bits of the 8-bit integer colour for an n-bit field. The ide VRAM test (no dither bit, flat fill) is a [source] software expectation against rounding to the nearest level: it expects red or green `0x24 * 5` = 180 to give level 5 (rounding gives 6) and blue `0x55 * 2` = 170 to give level 2 (rounding gives 3). Truncation passes it, and so would a proportional rescale of the byte to the field, which the test cannot exclude.

**Without the dither bit: truncation.** **[binary]** When the dither state is off, every routine that loads a colour adds a rounding constant itself before the store: 15.0 to red and green and nothing to blue in a single-buffered window (the two constants are stored by the context set-up code at 0x0daae31c and 0x0daae39c, inside the range of the nearest preceding export, `__glRexAllocAccum`, and read by `__glRexDownloadCurrentColor`, `__glRexSetInitialParameters`, `__glRexStoreRGBRoundedSpan` and the line routines), 0.0 for all three in a double-buffered window, and 0.5 for a colour index. With the dither bit set none of these is added. A chip that rounded by itself would not need them; so the chip is **inferred** to drop the bits below the field (the fraction included) with no rounding. The fifteen is half a step of the 3-bit field (step 32) less one, so it makes the cut fall at about the midpoint between two levels; blue and the 4-bit window get no offset and so have equal-width bins (blue: a colour of 0.5 selects level 1 of 3, not 2).

**The colour scales.** The 8-bit RGB initialiser (`__glRexInitRGB8`) stores 226, 226 and 255 for the three channels, the 4-bit initialiser (`__glRexInitRGB4`) 255 for all three. So an RGB8 window scales a unit colour to 0..226 for red and green and 0..255 for blue before the offset or dither, **[binary]**; the 3-bit fields are given a range of 226 rather than 255. **Inferred**, and only arithmetic on the constants: 226 plus the largest offset the driver adds with dither off (15) stays below 256, and 226 plus 29 is 255, so the driver keeps red and green at least 29 below full scale, which is the headroom it expects the dither to add. Whether the chip's dither adds, compares or saturates is **unknown**.

**With the dither bit: position-dependent.** The library draws software-generated pixels one at a time with the point word 0x3000c001 (`__glRexStoreRGBDitheredSpan`): `XSTARTI` is set per pixel, the three colours are written plus 6144.0 only, and the final colour store at its GO alias runs the draw. The chip is given the pixel position (`XSTARTI` per pixel, `YSTARTI` once) and a colour, and the library adds no rounding of its own when the bit is on, so the dither is **inferred** to depend on the position (x and y low bits); the routine would be written the same way for any dither, so it does not prove that. The matrix, its size and the amplitude are **unknown: no shipped software or published source depends on them.** Routes tried (2026-11-25): the ide sources (`minigl.c` only sets or clears command bit 15 from a shell switch; `vram.c`, `rexpatterns.c` and `cid.c` draw with it off or read back only flat fills; `rex.c` is register read-back), the 6.5.7 `libsk` LG1 code, the kernel and both PROMs (the command words listed on the [REX1 page](README.md) never carry bit 15), the IRIS GL `libgl.so` (`gl_i_dither`, `gl_c_dither`, `_dither` and `__GLdither` only set or clear 0x8000 in the context's command words, and `gl_d_dither` records the call), the 5.3 and 6.2 `lg1mc.so` (no dither table; the 16-entry permutation at 0x5e575bec in 6.2 is the exported `InverseAlu`, the X raster-operation inverse table) and the 5.3 and 6.2 kernels.

**The one dither table the GL ships is not the chip's.** **[binary]** `libGLcore.so` holds the textbook 4 by 4 ordered-dither matrix as 16 bytes at 0x0dbc4370 (rows 0 8 2 10, 12 4 14 6, 3 11 1 9, 15 7 13 5), read by `__glDitherRGBASpan` (0x0db21c8c) as entry `(x & 3) + 4 * (y & 3)`: it scales the colour by 16, adds the entry, shifts right by 4 and limits the result from above to the channel maximum. Only `__glGenericPickSpanProcs` (0x0db139e0) selects it, and `__glRexPickSpanProcs` replaces that pick (installed from `__glRexAllocAccum`), so the Entry board never runs it. It shows that the library's own software dither saturates at the top; it says nothing about the chip.

**What the library's constants bound (inferred).** With the dither bit off, red and green get a rounding offset of 15.0 before the 3-bit field drops its low 5 bits (a step of 32), which is half a step less one. A threshold set whose mean is about half a step is what the same output would need from a chip that adds a threshold, so a per-field amplitude of one step is the natural reading for the 3-bit fields. The scale 226 for the same two channels (section "The colour scales") leaves 29 below 255: either the largest threshold the chip adds is at most 29 or the chip saturates its sum. The 4-bit window uses scale 255 and no offsets, which leaves no headroom at all and so needs saturation if it dithers by adding. None of this fixes the matrix, its phase or whether the chip adds, compares or saturates.

**`FRACTION1`, `DITHERRANGE` and `AWEIGHT`.** All three are state the library sets once per context and never changes while drawing. **[binary]** `AUX1` for every GL context is 0x202 (single-buffered) or 0x222 plus the buffer bits (double-buffered), so `FRACTION1` (bit 1) and `DITHERRANGE` (bit 9) are always set, `FRACTION0` and the colour-compare bits always clear; the X server never sets any of them (its words are 0x28, 0x2c, 0x30). `AWEIGHT` is written 0xdb987642 once, in the context set-up code at 0x0daae684, together with `RWMASK` 0xff and `CONFIGMODE` 0x80084000 (under a context flag that was not decoded; the same constant is in `libgl.so` at 0x0f0a3494), and nothing in the 6.2 GL reads or rewrites it afterwards: the library antialiases lines in software (`__glRenderAntiAliasLine`), never with the chip's antialias opcodes. **Unknown** for all three: the names suggest a count of fraction bits and a dither amplitude range, and the weights' nibbles are 13, 11, 9, 8, 7, 6, 4, 2, but no shipped code that varies them exists.

**Differences between the 8-bit and 4-bit windows** are therefore all in the library: field widths (3-2-3 against 1-2-1), colour scales (226, 226, 255 against 255), rounding offsets (15, 15, 0 against 0, 0, 0 with dither off) and, for double buffering, the destination bits in `AUX1`. The command words are the same.

## 3. The colour DDA

**Register contents.** The library never writes a colour as an integer. It adds a constant to the floating-point value and stores the float's bit pattern: colours are `c + 6144.0` (bit pattern 0x45c00000 plus `c * 2048` for 0 <= c < 512), slopes are `m + 6144.0` for a positive slope and `m - 6144.0` for a negative one (0xc5c00000 plus `|m| * 2048` for negative m). The constant is initialised once at `0x45c00000` (and 256.0, 0x43800000, for the line slope, [true lines](true-lines.md)); the ide uses 4096.0 for the same purpose ([source] `minigl.c`, `REX_MCOLOR_NORM`). The effect is that the float's low mantissa bits are the fixed-point number: 11 fraction bits, the integer part above them, the rest of the word a constant the chip ignores. **Established** for the library; for the chip, see the next section for which bits it keeps. A colour of 100.5 therefore arrives as 0x45c00000 + 100.5 * 2048 = 0x45c32400.

**The rule.** **Software expectation, not measured.** The colour of pixel i of a shaded row is the start colour plus i times the slope, for each channel separately, with the start colour loaded at `XSTARTI`. The evidence: the ide `_polygon` loads the start colour as an integer into `COLORREDI` and computes the slope as 256 times the colour difference divided by (x1 - x0), so the colour reaches the end colour at the last pixel ([source] `minigl.c`); the GL's flat edge stepping and its slope calculation (`__glRexComputeSlopes`: the colour gradient across the triangle, one value per channel, 1 / area as the common factor) give the same per-pixel step. 11 fraction bits are the 11 low mantissa bits of the stored float, and the `COLORREDI` write to `COLORRED` read-back is `(value & 0xff) << 11` ([source] `rex.c`): the integer part of a colour sits at 18:11.

**Skipped pattern pixels.** The start colour stored for a masked row is the colour at the left edge, `XSTARTI`, not at the first pixel whose mask bit is set (`__glRexFillRGBGZSubTriangle` stores the left-edge colour once per row, then the depth routine decides the mask; the first mask bit is frequently clear). The library therefore expects the colour step to be taken for **every** pixel position, drawn or not. **Inferred** from that arithmetic (the only way those rows come out right). A model that advances the colour only on drawn pixels draws the wrong gradient wherever the mask has a gap.

**Wider than 32 pixels.** One `ZPATTERN` word covers 32 pixels, the leftmost in bit 31 (the pattern word of the trace has leading ones for the covered pixels); a longer row takes more words, and the colour continues from piece to piece (`SHADECONTINUE`, section 1).

**Underflow and overflow.** The colour stores in the trace include 0x45b... (the start colour is below zero), 0x45c8... to 0x45cf... (256 to 511) and a few 0x45d... (512 and above). They come from the left-edge extrapolation on slivers with steep gradients (the slopes reach about 250 colour steps per pixel). The library does not clamp them. **[binary]** The colour registers keep 20 bits (integer 18:11 and one more integer bit at 19, the header's type is nine integer and eleven fraction bits; [source] `rex.c`: the read-back mask is 0xfffff), so a negative colour is stored modulo 512 and appears as a high value. **Unknown:** whether the chip clamps, wraps, takes the ninth bit as a sign or lets the accumulator run past 255. A model must pick one; clamping to 0..255 is the safest and is an approximation to state, not hardware behaviour. The library's scale choices (section 2) are consistent with an author who did not rely on the chip saturating.

## 4. Slope sign: bit 31 or bit 19?

The chip honours **bit 31**, and the ide diagnostic states the rule. **[source]** `rex.c` writes patterns to each slope register and computes the expected read-back as follows (own words): keep bits 31 and 20:0 of the written value; when bit 31 is set, clear bit 20, negate the whole word, keep the low 21 bits; then set bit 20 to bit 19 (an OR with the bit already there). The 17-bit `MINORSLOPE` test keeps bit 31 and bits 16:0, clears bit 16 before the negation when bit 31 is set, and keeps 17 bits of the result; it has no step that copies a lower bit upward. The test writes only four patterns (0, 0x55555555, 0xaaaaaaaa, 0xffffffff), so the general rule is an inference from them. Bits 30:21 of a slope write are ignored. Reading it as sign and magnitude: **bit 31 is the sign, bits 19:0 are the magnitude (bit 20 is not part of the magnitude of a negative value), the stored value is the two's-complement of the magnitude, and it reads back sign-extended into bit 20.** That is exactly the float with the constant added: negative slopes arrive as sign bit 1 and a mantissa that is the magnitude. Bit 19 alone, with bit 31 clear, is a positive value (256 colour steps per pixel and up), not a sign; a positive store of 0x45c80000 reads back with bits 20 and 19 set. The `COLOR` registers have no such rule: the test masks 20 bits and expects them back unchanged, so bit 31 of a colour write is dropped. The library never sets it for a colour.

In the trace about half the slope stores begin 0xc5c (negative) and the rest 0x45c (positive); the neighbouring-row colours of the shaded rows fit the negative reading, as the run summary found.

## What a model must do

1. Command bits: accept 14, 15, 17, 20 and 25. Bits 14 and 17 select the three-channel colour and the slope stepping; bit 15 selects the dithered conversion; bit 20 continues the colour between 32-pixel pieces; bit 25 has no known effect and no shipped software depends on one (draw as clear; an approximation to state, not a gap to log).
2. `COLORRED`/`GREEN`/`BLUE` keep the low 20 bits (integer 18:11, fraction 10:0); `COLORREDI` (and green, blue) write `(v & 0xff) << 11` into the matching colour register.
3. `SLOPERED`/`GREEN`/`BLUE`: bits 31 and 20:0 are kept; bit 31 makes the value the 21-bit two's-complement of the magnitude; read back as stored with bit 20 ORed with bit 19. `MINORSLOPE`: bit 31 sign, 17 bits kept, bit 16 ignored in a negative magnitude, no bit copied upward ([true lines](true-lines.md)).
4. Shaded rows: colour at pixel i = start + i * slope. Per channel this is the software expectation; stepping at every pixel position from `XSTARTI` to `XENDI`, drawn or masked, is the inference of section 3. Keep the colour state across `ZPATTERN` words when bit 20 is set.
5. Pixel: take the top bits of each channel's 8-bit integer part (3-2-3 for the 8-bit window, 1-2-1 for the 4-bit window), with no rounding. With bit 15 set, add a position-dependent ordered-dither threshold first and saturate; the matrix and amplitude are an **approximation** with a stated limitation (no shipped evidence), so name it as one and keep it behind a switch the first reviewer can change. A 4 by 4 matrix of thresholds spread over one field step, indexed by the low two bits of x and y, is as good a choice as any; say in the model that the chip's own table is unknown.
6. Do not claim the library's software matrix as the chip's: it is the generic path's table and the Entry board never selects it.

Discriminating qtests (register contract only, predictions of the rules above; the ide test itself exercises only the four patterns named in section 4): write 0x45c00800 to `SLOPERED` and read 0x800; write 0xc5c00800 and read 0x1ff800; write 0xc5d00800 (bit 20 set in the magnitude) and read the same; write 0x12345678 to `COLORRED` and read 0x45678; write 0xff to `COLORREDI` and read 0x7f800. None of these depends on the dither or the pixel conversion.
