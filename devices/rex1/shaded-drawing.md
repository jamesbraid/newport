# REX1 shaded drawing: what the IRIX 6.2 GL sends for colour, dither and shaded spans

How the OpenGL library for the Indigo Entry board colours pixels: the command bits, the colour registers, the slope registers and the dither flag. The register list is in [registers.md](registers.md), the engine model on the [REX1 page](README.md), the buffer, mask and clip state the same library sets up on [GL context state](gl-context-state.md), and lines on [true lines](true-lines.md).

Grades follow [AGENTS.md](../../AGENTS.md). Tags: **[binary]** read in a shipped object with its address; **[source]** the IRIX source tree, by path; **[hdr]** a name from the shipped header `sys/lg1hw.h` (6.2 copy, revision 1.28; the names the Linux Newport header also carries are public); **[inferred]** says what it rests on. Everything here is what *software expects*: no register was measured on a board, and the library's own arithmetic is the only evidence for what the chip does with the values it is given.

Objects read, all from the IRIX 6.2 install media (`eoe.sw.gfx`, subsystem for the IP20 and the LG1MC graphics arch; hashes in [irix-files.md](../../references/irix-files.md)): `libGLcore.so` of `usr/gfx/arch/IP20LG1MC` (the OpenGL renderer; its exported `__glRex*` symbols name every routine below) and, for the shared constants only, `libgl.so` of the same directory. The IRIX source files cited are the ide diagnostics in `stand/arcs/ide/fforward/graphics/LIGHT/` (`minigl.c`, `rex.c`, `vram.c`, `rexpatterns.c`), which drive the same chip through the same registers. The dynamic symbol tables name the routines; the functions were read from first to last instruction by hand from a MIPS disassembly (no decompiler), so every reading is **established** for what the code stores and **inferred** for what the chip does with it. The Entry-run trace quoted for the observed words is a decoded log of `ivview` on the emulated Entry model (model output, not hardware evidence; it shows what the guest sends, which is all it is used for).

## What the guest sends for one shaded triangle row

`__glRexFillRGBGZSubTriangle` walks a triangle scan line by scan line; it has seven siblings (colour index or RGB, flat or smooth, with or without the depth mask; `__glRexFillRGBSubTriangle`, `__glRexFillCIGZSubTriangle` and the rest), and only this one was read from first to last instruction. **[binary]** Per row it stores, in this order: `XSTARTI` (0x0c) the left pixel, `XENDI` (0x84) the right pixel (the right edge minus one, an inclusive end), `YSTARTI` (0x1c) the row, `COLORRED`, `COLORGREEN`, `COLORBLUE` (0x3c, 0x44, 0x4c) the colour at the left pixel, `COMMAND` GO (0x800) with 0, `COMMAND` (0x000) with the row command, and then the depth routine writes the per-pixel mask word(s) to `ZPATTERN` GO (0x860). The slope registers (`SLOPERED`, `SLOPEGREEN`, `SLOPEBLUE`, 0x50, 0x54, 0x58) are written once per triangle by `__glRexComputeSlopes`, not per row. Host code, not the chip, steps the left edge from row to row (the left colour of the next row is computed on the host); the chip supplies only the step across the row. The Entry-run trace shows exactly this order for 5041 rows in one frame (the word 0x3212c5b1 is what `__glRexPickTriangleProcs` builds for a shaded, depth-masked RGB row, section 1), and about ten percent of rows with no mask store: the depth routine writes no word when every pixel of the row failed.

## 1. The command bits

The bits 14, 15, 17, 20 and 25 are all named in the shipped header and all built by `__glRexPickTriangleProcs` (0x0dab030c) and the span, point, line and clear routines. **[binary]**

0x8000 alone clearing the overlay and 0xc000 the pixel planes is therefore not a plane selector: both clears are the block fill 0x329 with the dither bit the GL always adds, and the plane group is `AUX2` bits 31:29 (2 for the overlay, 1 for the pixel planes, [plane groups](../../platforms/lg1/desktop-and-overlays.md#plane-groups)). Bit 14 is set in the second because that window is RGB. With the GL dither state off the same code issues 0x329 and 0x4329.

## 2. Colour to pixel: truncation or dither

**Pixel layouts.** The 8-bit TrueColor window is red 7:5, blue 4:3, green 2:0 ([source] `vram.c`: from the colour byte the test builds red as `0x24 *` bits 7:5, green as `0x24 *` bits 2:0 and blue as `0x55 *` bits 4:3, loads them through the three integer colour registers and expects a block fill in RGB mode to read back that byte). The 4-bit double-buffered window is red 3, green 2:1, blue 0: the colour map the X server loads for it has entry n red = bit 3, green = bits 2:1, blue = bit 0 ([colour-map install](../../platforms/lg1/colormap-install.md)). Both are the top bits of each channel; **inferred** that the chip keeps the top n bits of the 8-bit integer colour for an n-bit field. The ide VRAM test (no dither bit, flat fill) is a [source] software expectation against rounding to the nearest level: it expects red or green `0x24 * 5` = 180 to give level 5 (rounding gives 6) and blue `0x55 * 2` = 170 to give level 2 (rounding gives 3). Truncation passes it, and so would a proportional rescale of the byte to the field, which the test cannot exclude.

**Without the dither bit: truncation.** **[binary]** When the dither state is off, every routine that loads a colour adds a rounding constant itself before the store: 15.0 to red and green and nothing to blue in a single-buffered window (the two constants are stored by the context set-up code at 0x0daae31c and 0x0daae39c, inside the range of the nearest preceding export, `__glRexAllocAccum`, and read by `__glRexDownloadCurrentColor`, `__glRexSetInitialParameters`, `__glRexStoreRGBRoundedSpan` and the line routines), 0.0 for all three in a double-buffered window, and 0.5 for a colour index. With the dither bit set none of these is added. A chip that rounded by itself would not need them; so the chip is **inferred** to drop the bits below the field (the fraction included) with no rounding. The fifteen is half a step of the 3-bit field (step 32) less one, so it makes the cut fall at about the midpoint between two levels; blue and the 4-bit window get no offset and so have equal-width bins (blue: a colour of 0.5 selects level 1 of 3, not 2).

**The colour scales.** The 8-bit RGB initialiser (`__glRexInitRGB8`) stores 226, 226 and 255 for the three channels, the 4-bit initialiser (`__glRexInitRGB4`) 255 for all three. So an RGB8 window scales a unit colour to 0..226 for red and green and 0..255 for blue before the offset or dither, **[binary]**; the 3-bit fields are given a range of 226 rather than 255. **Inferred**, and only arithmetic on the constants: 226 plus the largest offset the driver adds with dither off (15) stays below 256, and 226 plus 29 is 255, so the driver keeps red and green at least 29 below full scale, which is the headroom it expects the dither to add. Whether the chip's dither adds, compares or saturates is **unknown**.

**With the dither bit: position-dependent.** The library draws software-generated pixels one at a time with the point word 0x3000c001 (`__glRexStoreRGBDitheredSpan`): `XSTARTI` is set per pixel, the three colours are written plus 6144.0 only, and the final colour store at its GO alias runs the draw. The chip is given the pixel position (`XSTARTI` per pixel, `YSTARTI` once) and a colour, and the library adds no rounding of its own when the bit is on, so the dither is **inferred** to depend on the position (x and y low bits); the routine would be written the same way for any dither, so it does not prove that. For REX1 the matrix, its size, its phase and the amplitude are **unknown: no shipped software or published source for this chip depends on them** (the sibling chip's published rules are below). Routes tried (2026-11-25): the ide sources (`minigl.c` only sets or clears command bit 15 from a shell switch; `vram.c`, `rexpatterns.c` and `cid.c` draw with it off or read back only flat fills; `rex.c` is register read-back), the 6.5.7 `libsk` LG1 code, the kernel and both PROMs (the command words listed on the [REX1 page](README.md) never carry bit 15), the IRIS GL `libgl.so` (`gl_i_dither`, `gl_c_dither`, `_dither` and `__GLdither` only set or clear 0x8000 in the context's command words, and `gl_d_dither` records the call), the 5.3 and 6.2 `lg1mc.so` (no dither table; the 16-entry permutation at 0x5e575bec in 6.2 is the exported `InverseAlu`, the X raster-operation inverse table) and the 5.3 and 6.2 kernels. Re-searched 2026-11-26: the IRIX 6.5 `libGLcore.so` and `libgl.so` of the same arch (new rows in [irix-files.md](../../references/irix-files.md)) have the same table, constants and `AUX1` words as 6.2; the 16-byte matrix, its eight rotations and mirrors and its scalings by 2, 4, 8, 16 and 17 occur in no held object but the two `libGLcore.so` copies (the 5.3, 6.2 and 6.5 server modules, `Xsgi`, `gfxinit`, both kernels, both PROMs and the `ide` image were scanned); `minigl.c` still only toggles the bit; searches of the Library's Usenet archive found one SGI remark on the hardware dither (below) and no table.

**The one dither table the GL ships is the generic software one.** **[binary]** `libGLcore.so` holds the textbook 4 by 4 ordered-dither matrix as 16 bytes at 0x0dbc4370 (rows 0 8 2 10, 12 4 14 6, 3 11 1 9, 15 7 13 5), read by `__glDitherRGBASpan` (0x0db21c8c) as entry `(x & 3) + 4 * (y & 3)`: it scales the colour by 16, adds a float kept in the context (offset 0xb38, not decoded) and the entry, shifts right by 4 and limits the result from above to the channel maximum. Only `__glGenericPickSpanProcs` (0x0db139e0) selects the dither routines, and the library holds no reference to that pick that was found (no call, GOT entry or data word). The Entry board's context set-up (0x0daae024, called from a static routine that `__glRexCreateContext` registers, unless bit 1 of the context flags at offset 0x90 is set; what that flag means was not decoded) stores `__glRexPickSpanProcs` in the context's span-pick slot (offset 0x2708, store at 0x0daae2a4) and the generic set-up stores `__glPixPickSpanProcs` there, so no path from the Entry board to the dither routines was found. It shows that the library's own software dither saturates at the top. Its 16 entries and its row and column order are those of the REX3 specification's matrix (below), as a library shared across boards would have; because the Entry board never reaches it, it is not evidence about REX1. The 6.5 copy is at file offset 0x103720 with the same readers.

**The sibling chip's published dither [sibling: established for REX3, not for REX1].** The REX3 specification (Library `erikarn-sgi_indy_rex3.pdf`; sections 3.8.2 and 3.8.3 on PDF pages 72 to 74, the dithering block of section 5.4.3.2 on page 144, the register tables on pages 21 to 25, DRAWMODE1 on page 25) describes the dither of the chip that followed REX1. In my words: the matrix is the 4 by 4 ordered (Bayer) one, rows by y and columns by x, 0 8 2 10 / 12 4 14 6 / 3 11 1 9 / 15 7 13 5 (read from the figure on page 72). The entry is picked by the two low bits of the *window-relative* x and y, which the chip carries beside each pixel under that name and apart from the screen address. A pixel goes up one level of its field when a four-bit value is greater than the entry. For RGB that value is the four bits just below the field in the scaled 8-bit colour (the integer part: section 3.8.2.1 compares S[3:0]; the page-144 diagram lists the 11-bit fraction, bits 10:7, among the compare inputs, and section 3.8.2.2 gives that fraction to colour index); for colour index it is the top four fraction bits. For RGB fields of 1 to 4 bits the colour is first scaled down (by 1/2, 3/4, 7/8 and 15/16) so the added level cannot brighten the image or clamp; 24-bit RGB is not dithered. For colour index nothing is scaled and the fraction is clamped first so the step cannot overflow. With the dither bit clear that chip rounds to the nearest level itself (RGB: the field plus the next bit of the scaled colour; colour index: plus one when the fraction's top bit is set). The enable is DRAWMODE1 bit 16, next to RGBMODE at bit 15, which picks RGB or colour-index behaviour for shading, rounding, dithering, comparing and clamping. The public drivers add nothing: NetBSD `sys/arch/sgimips/gio/newportreg.h` (Library snapshots d894b81 and 07004b2a), OpenBSD `sys/arch/sgi/gio/newportreg.h` (2df91d80) and Linux `include/video/newport.h` give the bit's name and value and never compute a dither (re-searched 2026-11-26; the MAME REX3 source is not in the Library snapshots, and the MAME Entry-board model draws no dither).

**One published statement about REX1 itself [published; established only for the existence of the hardware dither].** A comp.sys.sgi post of 30 July 1991 by an SGI employee (Message-ID `<1991Jul30.205022.19339@zola.esd.sgi.com>`; his signature gives Silicon Graphics, Inc., and he says he is not the expert on Indigo graphics) says the REX chip has hardware support for colour dithering, so the GL can work in 24-bit colour and REX dithers into the colour map when it draws, and that double-buffered RGB windows look worse because REX dithers into a 16-entry map (four planes per buffer). It gives no matrix, size or arithmetic.

**What ties REX1 to REX3 [inferred; by lineage].** The specification says REX3 is based on some of REX1's concepts and names REX1 differences in several places (the copy offset is to the source on REX1 and to the destination on REX3, software subtracts the DMA start byte from the start x on REX1 and the chip does it on REX3, sub-24-bit colours are written through colour-index mode on REX1). The register shapes the `ide` test pins on REX1 are REX3's: 20-bit colour registers with one overflow bit, eight integer bits and eleven fraction bits, and slopes written as sign and magnitude and stored as two's complement. The command bits carry the same names (`STOPONX` and `STOPONY` even at the same bit numbers, 8 and 9; `ENZPATTERN`, `ENLSPATTERN` and `LSADVLAST` in the same order; `LSOPAQUE`, `SHADE`; the logic operation in the top four bits), and the RGB-mode and dither pair keeps its order (REX1 bits 14 and 15, REX3 DRAWMODE1 bits 15 and 16). For colour index both chips would dither from the same 11-bit colour fraction; REX3's RGB compare uses the scaled integer bits instead, so for RGB the shared fraction width does not bear on it.

**Where REX1 is known or inferred to differ [inferred].** (a) REX3 rounds in hardware when the dither bit is clear; the GL adds its own offsets for REX1 (15.0, 0.5), so REX1 truncates. (b) REX3 scales RGB internally to make headroom. Nothing shows such a step on REX1: the GL's red and green scale of 226 is consistent with its own rounding (next paragraph), so it does not by itself show headroom for a dither, and it gives full-scale blue (a 2-bit field) and every channel of the 4-bit window an unscaled 255 with the dither bit on by default, which a chip that added a threshold could only draw correctly if it saturated on carry, scaled internally as REX3 does, or compared so that no carry arises. (c) REX1 has `AUX1` bits (`FRACTION1:0`, `DITHERRANGE`) that REX3 has no counterpart for, so whatever they control, the REX3 text cannot say. These are reasons the REX3 rules cannot be taken whole for REX1; they are not evidence about the matrix.

**What the library's constants bound (inferred).** The constant 226 needs no dither explanation, but nothing here singles it out either. With the rounding offset 15, the boundaries between the eight levels of a 3-bit field fall at c = 32j - 15 for j = 1 to 7 (17, 49, 81, 113, 145, 177, 209); equal-width bins around the seven levels of a unit colour scaled to 226 need them at 226 (2j - 1) / 14 (16.1, 48.4, 80.7, 113.0, 145.3, 177.6, 209.9), which agrees to within one count, and the fourth boundary, 113, is exactly half of 226. So 226 is consistent with rounding with offset 15. It is not fixed by it: any scale from 224 to 227 agrees to within one count, and 224 is REX3's own 7/8 scale for a 3-bit field, so the constant neither shows nor excludes headroom for the chip's dither (the earlier reading, 226 plus 29 reaching 255, fits equally). What does bear on the chip is the dither-on case: the GL adds no offset and sends blue at 255 into a field of four levels (step 64) and 255 into the 1-bit and 2-bit fields of the 4-bit window. A chip that added a threshold and wrapped on carry would draw full-intensity blue (and every saturated channel in the 4-bit window) as black on most pixels, which the first test would have shown. REX1 is therefore **inferred** not to wrap visibly on a carry out of the top of a field: it saturates, scales internally or never carries there, and nothing read tells these apart. A per-field amplitude of one step is the natural reading (the mean threshold then equals the half-step the GL adds when it rounds itself), but nothing fixes it, the matrix, its phase or whether the chip adds, compares or scales.

The command words are the same.

## 3. The colour DDA

**Register contents.** The library never writes a colour as an integer. It adds a constant to the floating-point value and stores the float's bit pattern: colours are `c + 6144.0` (bit pattern 0x45c00000 plus `c * 2048` for 0 <= c < 512), slopes are `m + 6144.0` for a positive slope and `m - 6144.0` for a negative one (0xc5c00000 plus `|m| * 2048` for negative m). The constant is initialised once at `0x45c00000` (and 256.0, 0x43800000, for the line slope, [true lines](true-lines.md)); the ide uses 4096.0 for the same purpose ([source] `minigl.c`, `REX_MCOLOR_NORM`). The effect is that the float's low mantissa bits are the fixed-point number: 11 fraction bits, the integer part above them, the rest of the word a constant the chip ignores. **Established** for the library; for the chip, see the next section for which bits it keeps. A colour of 100.5 therefore arrives as 0x45c00000 + 100.5 * 2048 = 0x45c32400.

**The rule.** **Software expectation, not measured.** The colour of pixel i of a shaded row is the start colour plus i times the slope, for each channel separately, with the start colour loaded at `XSTARTI`. The evidence: the ide `_polygon` loads the start colour as an integer into `COLORREDI` and computes the slope as 256 times the colour difference divided by (x1 - x0), so the colour reaches the end colour at the last pixel ([source] `minigl.c`); the GL's flat edge stepping and its slope calculation (`__glRexComputeSlopes`: the colour gradient across the triangle, one value per channel, 1 / area as the common factor) give the same per-pixel step. 11 fraction bits are the 11 low mantissa bits of the stored float, and the `COLORREDI` write to `COLORRED` read-back is `(value & 0xff) << 11` ([source] `rex.c`): the integer part of a colour sits at 18:11.

**Skipped pattern pixels.** The start colour stored for a masked row is the colour at the left edge, `XSTARTI`, not at the first pixel whose mask bit is set (`__glRexFillRGBGZSubTriangle` stores the left-edge colour once per row, then the depth routine decides the mask; the first mask bit is frequently clear). The library therefore expects the colour step to be taken for **every** pixel position, drawn or not. **Inferred** from that arithmetic (the only way those rows come out right). A model that advances the colour only on drawn pixels draws the wrong gradient wherever the mask has a gap.

**Wider than 32 pixels.** One `ZPATTERN` word covers 32 pixels, the leftmost in bit 31 (the pattern word of the trace has leading ones for the covered pixels); a longer row takes more words, and the colour continues from piece to piece (`SHADECONTINUE`, section 1).

**Underflow and overflow.** The colour stores in the emulated-run trace include 0x45b... (the start colour is below zero), 0x45c8... to 0x45cf... (256 to 511) and a few 0x45d... (512 and above). They come from the left-edge extrapolation on slivers with steep gradients (the slopes reach about 250 colour steps per pixel). The library does not clamp them. **[binary]** The colour registers keep 20 bits (integer 18:11 and one more integer bit at 19, the header's type is nine integer and eleven fraction bits; [source] `rex.c`: the read-back mask is 0xfffff), so the integer part is held modulo 512: a colour of -3 is stored as the float 6141.0, whose low 20 bits read as integer 509, and a colour of 300 arrives as 300.

**What the chip does with those values is unknown: no shipped software depends on it** (re-searched 2026-11-25: the ide sources, both PROMs, the kernels, both X server modules, both GL libraries). The only related software fact is the ide `_polygon` in `minigl.c`, which computes each row's start colours in floating point and prints a diagnostic when one falls below 0 or reaches 256: its author treated an out-of-range colour as a fault to report, not as something the chip would clamp, and the diagnostic is the only check. The 9-bit field cannot be read so that both of the GL's overshoot directions come out right: as an unsigned count, saturating at 255, a negative colour (stored as 512 minus its size) lands in 256 to 511 and would draw white; as a signed value, saturating at 0 and 255, a positive overshoot to 256 to 511 would draw black; taking the low eight bits gets both wrong. So the shipped GL either produces visibly wrong fringe pixels on slivers or relies on a chip behaviour that neither of those two readings explains. **Inferred**, from the register width only.

**Sibling reading (2026-11-26) [inferred].** The REX3 specification (section 3.8, PDF page 70, and the register table on page 22) gives its green, blue and alpha colour registers the same 20-bit shape (one overflow bit, eight integer, eleven fraction; its red register is wider because it also carries 12-bit colour index) and says each iteration of the colour is clamped before the pixel path, the nine integer bits covering a range of minus one half to plus one and a half. Read that way, a REX1 integer field of 0 to 383 is a colour of 0 to 1.5 (draws 255 when above 255) and 384 to 511 a colour of minus 0.5 to 0 (draws 0). Unlike the two readings above it gives both of the GL's overshoot directions the result it needs: a left-edge extrapolation of -3 (stored as 509) draws 0 and a colour of 300 draws 255. Only the few stores with an integer part of 384 to 511 (0x45cc... to 0x45cf...) would read as small negatives and draw 0. The reading rests on the shared register shape and the GL's two cases; nothing for REX1 states it. A model may use it, labelled an approximation.

A model must pick one and call it an approximation. The least harmful reading given the library's sizes: keep the 20-bit register value as stored and, when forming the pixel, treat the nine integer bits as a signed number (256 to 511 read as -256 to -1) and saturate to 0 to 255; or, to favour small positive overshoot, read 256 to 383 as 255 and 384 to 511 as 0. Neither is evidence; the first is simpler.

## 4. Slope sign: bit 31 or bit 19?

The chip honours **bit 31**, and the ide diagnostic states the rule. **[source]** `rex.c` writes patterns to each slope register and computes the expected read-back as follows (own words): keep bits 31 and 20:0 of the written value; when bit 31 is set, clear bit 20, negate the whole word, keep the low 21 bits; then set bit 20 to bit 19 (an OR with the bit already there). The 17-bit `MINORSLOPE` test keeps bit 31 and bits 16:0, clears bit 16 before the negation when bit 31 is set, and keeps 17 bits of the result; it has no step that copies a lower bit upward. The test writes only four patterns (0, 0x55555555, 0xaaaaaaaa, 0xffffffff), so the general rule is an inference from them. Bits 30:21 of a slope write are ignored. Reading it as sign and magnitude: **bit 31 is the sign, bits 19:0 are the magnitude (bit 20 is not part of the magnitude of a negative value), the stored value is the two's-complement of the magnitude, and it reads back sign-extended into bit 20.** That is exactly the float with the constant added: negative slopes arrive as sign bit 1 and a mantissa that is the magnitude. Bit 19 alone, with bit 31 clear, is a positive value (256 colour steps per pixel and up), not a sign; a positive store of 0x45c80000 reads back with bits 20 and 19 set. The `COLOR` registers have no such rule: the test masks 20 bits and expects them back unchanged, so bit 31 of a colour write is dropped. The library never sets it for a colour.

In the trace about half the slope stores begin 0xc5c (negative) and the rest 0x45c (positive); the neighbouring-row colours of the shaded rows fit the negative reading, as the run summary found.

## What a model must do

1. Command bits: accept 14, 15, 17, 20 and 25. Bits 14 and 17 select the three-channel colour and the slope stepping; bit 15 selects the dithered conversion; bit 20 continues the colour between 32-pixel pieces; bit 25 has no known effect and no shipped software depends on one (draw as clear; an approximation to state, not a gap to log).
2. `COLORRED`/`GREEN`/`BLUE` keep the low 20 bits (integer 18:11, fraction 10:0); `COLORREDI` (and green, blue) write `(v & 0xff) << 11` into the matching colour register. When a pixel is formed, read the nine-bit integer part as -128 to 383 and clamp it to 0 to 255 (the sibling reading of section 3: **inferred**, an approximation to name).
3. `SLOPERED`/`GREEN`/`BLUE`: bits 31 and 20:0 are kept; bit 31 makes the value the 21-bit two's-complement of the magnitude; read back as stored with bit 20 ORed with bit 19. `MINORSLOPE`: bit 31 sign, 17 bits kept, bit 16 ignored in a negative magnitude, no bit copied upward ([true lines](true-lines.md)).
4. Shaded rows: colour at pixel i = start + i * slope. Per channel this is the software expectation; stepping at every pixel position from `XSTARTI` to `XENDI`, drawn or masked, is the inference of section 3. Keep the colour state across `ZPATTERN` words when bit 20 is set.
5. Pixel: take the top bits of each channel's 8-bit integer part (3-2-3 for the 8-bit window, 1-2-1 for the 4-bit window), with no rounding. With bit 15 set, add a position-dependent ordered-dither threshold first and saturate at the top of the field (never wrap). The matrix, its phase and the amplitude are an **approximation** with a stated limitation (nothing states them for REX1): the least-wrong choice is the REX3 4 by 4 Bayer matrix, indexed by the low two bits of x and y relative to the window origin (`XYWIN`), compared against the four bits that lie just below the field, with the threshold spread over one field step. Say in the model that REX3's matrix is a sibling's, that REX1's own is unknown, that the weakest part is the phase (window against screen) and that the `AUX1` bits `FRACTION1:0` and `DITHERRANGE` are stored and ignored. Keep it behind a switch the first reviewer can change.
6. Do not claim the library's software matrix as the chip's: it is the generic path's table and the Entry board never selects it (it does equal the REX3 matrix, so the model's choice above gives the same numbers).

Discriminating qtests (register contract only, predictions of the rules above; the ide test itself exercises only the four patterns named in section 4): write 0x45c00800 to `SLOPERED` and read 0x800; write 0xc5c00800 and read 0x1ff800; write 0xc5d00800 (bit 20 set in the magnitude) and read the same; write 0x12345678 to `COLORRED` and read 0x45678; write 0xff to `COLORREDI` and read 0x7f800. None of these depends on the dither or the pixel conversion.
