# LG1: the Indigo Entry graphics board

The Entry ("Starter", LG1) graphics board of the SGI Indigo: a REX1 raster engine, a VC1 video controller with its SRAM, a
colour map, a pixel clock generator and eight memory chips on the photographed board (a 1024 by 768 frame buffer at 8 bits per pixel: the resolution and depth are established, the chip count is observed).
This page is the board-level account: what it is, where it sits, how the PROM and IRIX find and drive it. Register detail is in the
chip pages: [REX1](../../devices/rex1/README.md), [VC1](../../devices/vc1/README.md),
[Bt479 and LUT1](../../devices/bt479/README.md).

Grades follow [AGENTS.md](../../AGENTS.md). This is the **Indigo** (IP20 R4000 board; the PROM listing is also the base for the
IP12 R3000 board, which was not read here). The Entry board of the R3000 Indigo is the same board family; the facts below are
read from IP20 objects and PROMs and apply to the IP12 only where its PROM or kernel was read (it was not): **inferred** for IP12.
The Crimson also took an LG1; NetBSD says its register offsets differ significantly, so nothing here applies to it.

## Where it sits: GIO and addresses

Do not duplicate: the graphics slot, the probe addresses and the probe sequence are on the chips repository page `platforms/ip20/gio.md`. In short (all
established there): the board lives in the 4 MiB graphics window of the GIO space at 0x1f3f0000, with a second head at
0x1f3f8000; the LG1 does not answer the GIO product-ID read; and the board interrupts on GIO lines 0 (FIFO) and 2 (retrace),
INT2 local 0 bit 0 and local 1 bit 7 (see the chips repository's `devices/int2/README.md`).

What the probe's registers mean, from the REX side (the new part):

1. Store 0x12345678 at base + 0xc: this is `XSTARTI`. Only its low 12 bits stick (the ide register test masks it with 0xfff).
2. Store 0 at base + 0: `COMMAND` = no-op.
3. Read base + 0x800: the GO alias of `COMMAND`; this executes the no-op, which also makes the chip capture the pending coordinate.
4. Read base + 0x14: `XSTART`, the combined integer-and-fraction start x. It returns the 12-bit integer in bits 26:15:
   0x678 << 15 = 0x033c0000, the value the probe compares with. A flat read/write register at that offset cannot pass; a model
   needs XSTART to derive from XSTARTI (and the PROM expects the same on the second head). Established from `lightProbe`
   (`light_init.o`) and the PROM probe at 0xbfc0f9a8 (4.0.5D) / 0xbfc12858 (4.0.5G), as the page above records.
5. Before step 1 the kernel's `lightProbe` waits for `CONFIGMODE` bit 0 (busy) to clear, polling up to 300000 times: a board
   that is stuck busy is treated as absent. The PROM's probe has no wait (it stores first, reads later).

NetBSD probes differently: it requires the `XYWIN` register to read 0x08000800 (its `XYOFFSET`) after the PROM has
initialised the board. A model that initialises `XYWIN` to 0x08000800 on first PROM access passes both; a model whose
`XYWIN` resets to 0x08000800 passes NetBSD without help. The reset value of `XYWIN`: unknown (no shipped code reads it before
writing it).

## What the PROM does (IP20 4.0.5D and 4.0.5G)

Mostly established; the PROM routines are read by listing, function by function for the routines named, with the larger
initialisation function (0xbfc0fd00, 4.0.5D) matched against the kernel's by its stores rather than read line for line, so the
claim "the PROM initialises the board exactly as the kernel does" is **inferred**.

- **Probe loop.** A table at 0xbfc4d1f0 (4.0.5D) lists the board addresses 0xbf3f0000, 0xbf3f8000, 0. The loop at
  0xbfc10320 calls the probe (0xbfc0f9a8) on each, stops at the first board found, saves its address at 0xa8741260 and calls
  the board init (0xbfc102a8), which runs, in order: board info (0xbfc0fa00), colour map and clock (0xbfc0fb84), REX and VC1
  (0xbfc0fd00), and the palette entries for the console colours. The second loop at 0xbfc103e8 registers each board found as an
  ARCS display node named `SGI-LG1` with a `LG1MC` string and the display type constants; the strings are at 0xbfc4d220 and
  0xbfc4d228 (4.0.5D). The GR2 probe is tried first on the console path (callers 0xbfc0f6dc and 0xbfc0f814 in the chips
  page) and, if it answers, the LG1 loops are not needed: the order between the two families was not traced.
- **Board info.** `0xbfc0fa00` copies the 16-byte name "LG1MC" into the info block, stores 1024 and 768 as halfwords at
  info + 0x20 and + 0x22 and 0x34 at info + 0x24, reads the `WCLOCK` configuration byte (revision at info + 0x28, monitor
  type at info + 0x2b, a flag at + 0x2c set when bit 6 of the byte is clear), runs the pixel-memory probe (info + 0x29) and
  the VC1 revision read (info + 0x2a). The same fields in the kernel's board info structure are what `lightInfo` copies to user
  space: 0x34 bytes in all. **Established** for the layout as stored; unknown: what each of the three codes at + 0x29 means.
- **Console function table.** The PROM exports ten routines in a table at 0xbfc54040 (4.0.5D); 4.0.5G has its own copy at a
  different address. In table order, with addresses in 4.0.5D: blank/unblank (0xbfc2d430: `CONFIGSEL` 6 read-modify-write
  of VC1 SYS_CTL bit 2), set foreground colour (0xbfc2d4b0: store at 0xa87456b8, `COLORREDI` = colour), set one palette entry
  (0xbfc2d4e8), fill rectangle (0xbfc2d5c0: command 0x30000329), plot point (0xbfc2d620: 0x30000001), set current position
  (0xbfc2d670: store at 0xa87456b0, 0xa87456b4), draw bitmap (0xbfc2d684: the glyph blit, below), copy rectangle
  (0xbfc2d9f8: `XYMOVE` plus 0x30080329, for scrolling), report screen size (0xbfc2dab0: returns the 1024 and 768 halfwords stored
  in the board info), set cursor position (0xbfc2dad0: VC1 registers 0x22 and 0x24). **Established** for each routine's
  stores as listed (read through the whole routine).
- **Font blit path.** The PROM's console draws text with the drawing-bitmap routine: for a glyph at the current position it
  loads `XSTARTI` (x minus the glyph origin), `YSTARTI` (767 minus the y position, offset by the glyph origin), `XENDI`
  = x + width - 1 and `YENDI` = 0, writes the `COMMAND` GO alias with 0 (a no-op that latches the coordinates), writes the
  `COMMAND` 0x300005b9 (width up to 16 pixels: one command, then one `ZPATTERN` GO write per glyph row, the row's 16 bits in
  the top half) or the `a1`/`a9` piece commands (wider glyphs), then advances the current position by the glyph's advance.
  The glyph pixels come from a bit-per-pixel bitmap in the PROM image; transparent background. Screen scrolling uses the copy-rect
  routine, clearing uses fill-rect. **Established** for the register sequence; the PROM's own font and the console geometry
  (rows, columns) were not extracted: see the open questions.
- **What it probes first**: the REX probe described above, before anything else is written; the monitor type and revision are
  read in the board info step and decide the colour map path (revision below 2: Bt479 path).

## What IRIX does (6.5 IP20boot `lg1.a`)

Established from the member objects; the function names are the objects' own symbols.

- `lg1_earlyinit` (called early in boot): loops over the two-entry board table in `light.o` (addresses 0xbf3f0000 and
  0xbf3f8000 as kseg1 words), calls `lightProbe` on each and, for boards found, either only reads the board info and sets up the
  cursor (when the PROM console is on this board: the console argument's first byte is 'g' and the board has been initialised
  once already) or runs `lightInit` in full; then registers the board's `htp` function table (`lg1_htp_fncs` for revision
  below 2, `lg2_htp_fncs` otherwise) for the kernel's own console text path.
- `lg1_init`: allocates a 0x124-byte per-board structure for each board found, records it in the inventory (class 7 graphics,
  type 10, controller number), initialises its retrace state (`lightRetraceInit`), registers it with the graphics manager
  (`GfxRegisterBoard`), then sets bit 3 of the INT2 port register to enable retrace interrupts (with a bus flush) and installs
  `lightFIFO` on GIO line 0 and `lightRetrace` on line 2.
- `lightRetrace`: counts, calls the retrace handler, then pulses INT2 port register bit 3 clear and set to acknowledge. The
  retrace handler (`lightRetraceHandler`) walks 32 swap slots, performs pending buffer swaps by toggling bit 1 of the display-mode
  entry in the VC1 window and runs the retrace callbacks. Established; the VC1 side of what generates the retrace: unknown (no
  shipped code sets a VC1 field for it).
- User-visible entry points (the object's table at `.data` 0x28 onward): info, attach, detach, initialize, download, start,
  position-cursor, create/destroy display-rendering-node, validate-clip, null-clip, map/unmap graphics (`lightMapGfx` maps 0x5000
  bytes: the register file and its GO aliases), pcx swap/switch, swap-buffer scheduling, display mode, suspend, resume, set
  destination planes, set screenmask, get geometry, read display (colour maps and display modes), AUX1 register, private ioctl, and a
  pixel DMA entry. A model that supports the PROM console needs none of these; a model that supports IRIX needs the whole register
  file, the retrace interrupt and DMA.
- **X server.** See [Kernel and X server](#kernel-and-x-server-irix-53-and-65-what-the-model-needs-beyond-the-prom) below: the server loads `lg1mc.so` and draws through the same mapped register page.

## What a QEMU implementer needs, in order

1. A GIO device at 0x1f3f0000 (32 KiB window) with 32-bit big-endian registers as in the REX1 list, GO aliases at + 0x800, and the
   `XSTART` derived-register behaviour for the probe.
2. `CONFIGMODE` bit 0 reads 0.
3. A clock/config port that returns a board revision below 2 (so the PROM and IRIX take the Bt479 path), a monitor type, and bit
   6 = 0 (video board present).
4. The `CONFIGSEL`-addressed ports: write storage for the colour map (256 x 3 bytes, bank 0 enough for the PROM), the VC1 SRAM
   (at least 0x4900 bytes), the VC1 revision window (return a value whose low three bits are not 0 or 1; software subtracts one, and a result of 0 skips VC1 initialisation), SYS_CTL.
5. An 8 bpp 1024 by 768 frame buffer scanned out through the colour map (video on = SYS_CTL bit 2).
6. Commands 0x30000329, 0x30080329, 0x30000001, 0x300005b9, 0x300005a1/0x300005a9, with display row = stored y (see the REX1 page, Y origin; rows advance toward `YENDI`), and the plain
   register store semantics for everything else.
7. The PROM's board info runs a pixel-memory probe with three commands through `RWAUX1` ([REX1 page](../../devices/rex1/README.md#the-pixel-memory-probe-commands)); either outcome code 0 or 1 satisfies it.
8. For IRIX: retrace interrupt (GIO line 2, INT2 local 1 bit 7, with the port register bit 3 acknowledge), the FIFO interrupt on
   line 0 optional, and the pixel DMA entry.

The sources, with checksums, are in [irix-files.md](../../references/irix-files.md). ### Kernel: probe and initialisation

- **Order [binary].** `lg1_earlyinit` (`light.o` +0x21f8) loops over the two board addresses (0xbf3f0000, 0xbf3f8000) and runs `lightProbe` on each. When the PROM console is on the graphics head (first byte of the console argument is `g`) and this is the first call, it only runs `lightInitInfo` and `initLg1Cursor`; otherwise it runs `lightInit`: `initRex`, `rexClear`, `lightInitInfo`, `rexClear`, `initClock`, the colour map (`initLUT1` for revision 2 and up, `initBt479` below), then `initVC1` only if the VC1 revision byte is above 0 (else the console message "lg1 init: can't support old VC1s."). So with `console=g` the kernel keeps the PROM's register, colour map, clock and VC1 state and only reads the board and rewrites the cursor registers.
- **`lightProbe` (`light_init.o` +0x0) [binary].** `flushbus`, then up to 300000 reads of `CONFIGMODE` bit 0 with a one microsecond delay each (not busy: continue; still busy after 300000: board absent), then the XSTARTI/XSTART test already described above. Reads: `CONFIGMODE`, the `COMMAND` GO alias (0x800), `XSTART`.
- **`rexClear` (+0xa4) [binary].** For each of two passes (`AUX2` 0x40000000, then 0x20000000) it waits for not busy and stores `COMMAND` 0x329, `XSTATE` 0x03ff0000, `XSTARTI` 0, `YSTARTI` 0, `XENDI` 1023 and `YENDI` 767 at its GO alias. The command has an empty logic-operation nibble: the operation, mask and colour come from `XSTATE` (operation 3 replace, mask 0xff, colour 0). This is the model's first use of `XSTATE`; see [REX1](../../devices/rex1/registers.md).
- **`initRex` (+0x9a0) [binary].** Wait not busy, `XYWIN` 0x08000800, `CONFIGMODE` 0x807fe000, `AUX2` 0x20000000, GO store 0 at `COMMAND`, `AUX1` 0. Same as the PROM.
- **`lightInitInfo` (+0x9e8) [binary]**, in order: copy "LG1MC" into the record; store 1024 and 768 as halfwords at +0x20 and +0x22 and the size 0x34 at +0x24; `CONFIGSEL` 4, GO read of `WCLOCK`, one microsecond, read of `WCLOCK`: bits 2:0 to +0x28 (revision), bits 5:3 to +0x2b (monitor type), bit 6 to +0x2c (0 when set, 1 when clear); read `CONFIGMODE` and, when bits 7:4 are 0, run the pixel-memory probe (write 0x30200021 and 0x30210021, read with 0x30200023, with two reads of `RWAUX1` GO of which the second is compared: 0x01080909 gives byte +0x29 = 0, 0x09091020 gives 1, anything else 0xff; when bits 7:4 are not 0 the byte is that value plus one); `CONFIGSEL` 5 and 4 set the VC1 address to 5, `CONFIGSEL` 3, GO read, one microsecond, read `RWVC1`: byte +0x2a = (value & 7) - 1. The pixel-memory probe leaves test pixels in the frame buffer, which is why `lightInit` clears again afterwards.
- **MC virtual-DMA self-test (once per boot, `lightInitInfo` +0xba0 to +0xc70 and `tst_vdma_intr` +0xdd4) [binary].** Not used by the PROM. With interrupts off, clear bit 13 of the MC `cpuctrl0` (0x1fa00004), save the INT2 local 0 mask byte (0x1fb801c7) and set it to 0x10 (only the graphics-DMA bit), then `tst_vdma_intr`: write the MC DMA registers (`dma_ctl` +0x16c with `ie` set and `xlate` clear, then `dma_memadr` 0x1fa02004 to the physical address of a static word, `dma_mode` 0x1fa02034 = 0x5a, `dma_stride` 0x1fa0201c = 0x10000, `dma_size` 0x1fa02014 = 0x10004, and `dma_gio_adrs` 0x1fa0202c = 0x89abcdef, which starts it; per the MC page that mode is a memory fill and the value is the fill constant, so the board is not involved), poll `dma_run` (0x1fa0204c) bit 6 until it clears or 1000 microseconds pass, then test Cause bit 10 (`getcause() & 0x400`). If it is set, bit 6 of info byte +0x30 and of a driver flag are set; byte +0x30 also carries the MC revision level in the low bits and bit 7 always. Afterwards the MC and INT2 words are restored, `dma_cause` (+0x164) is cleared and `VdmaInit` runs. `lightInfo` (+0x168) prints "Prototype HP2 hardware" once when bit 6 is clear; the full trace and what the model must supply are on [the warning page](prototype-hp2-warning.md). The test does not fail the boot; the poll ends at once when `dma_run` bit 6 reads 0, so it costs 1000 microseconds only in a model that leaves that bit set. The meaning of the MC-side registers is on the MC page of the chips repository (`devices/mc`, graphics DMA engine); here only the sequence and the sink matter: the model needs the DMA-done interrupt (INT2 local 0 bit 4, Cause bit 10) to assert, or the flag and the pixel-DMA decisions below see an old machine. **[inferred]** from `tst_vdma_intr` only: byte +0x30 bit 6 means "the graphics DMA interrupt works".
- **Colour map and clock [binary].** `initClock` (+0x8a0) writes the 17-byte clock table through `WCLOCK` (`CONFIGSEL` 2), the table chosen by revision. `initBt479` (+0x25c) and `initLUT1` (+0x194) only write (the same bytes the [colour map page](../../devices/bt479/README.md) lists); no read or compare follows. `initVC1` (+0x594), `vc1LoadSRAM` (+0x528) and `initLg1Cursor` (+0x7e8) only write, except that `vc1LoadSRAM` reads the unused word at +0x7fc after each SRAM byte and discards it.

### Kernel: the user-visible interface

- **Mapping the register file [binary].** `lightAttach` (`light.o` +0x20c) maps 0x5000 bytes into the calling process (`lightMapGfx` +0xec8 builds the five page entries: physical page, flags 0x40000016 = valid, dirty, uncached). User code therefore reaches every register up to and including the GO aliases of `RWDAC` and `RWVC1` (0x4fe8, 0x4ff0, offsets below 0x5000) with ordinary loads and stores. The model must not trap or fault on user-mode accesses, and the aliases at 0x800 to 0x88c and 0x4fe0 to 0x4ffc must work from user mode.
- **Board info [binary].** `lightInfo` copies at most 0x34 bytes of the record built by `lightInitInfo` to the caller (the X server's `ddxGetBoardInfo` hands the same record to the module): name at +0x00, width and height halfwords at +0x20 and +0x22, size +0x24, revision +0x28, pixel-memory code +0x29, VC1 revision +0x2a, monitor type +0x2b, a word at +0x2c (1 when WCLOCK bit 6 is clear, 0 when set; see the review below for what the module does with it), flags byte +0x30. The module reads revision (to pick the Bt479 or LUT1 paths), pixel-memory code (`ddxGetBoardName` uses it for the name of the Express boards only), VC1 revision, monitor type (to pick `lg1MonitorSizeTable`), the flags byte (to pick the pixel-DMA path and the FIFO level) and the +0x2c word (`rexGetRevs` copies it; `rexInit` and the image and tile paths branch on it).
- **Private requests [binary].** `lightPrivate` (+0x1e80) accepts seven request numbers, 20001 to 20007, each with a small argument block: 20001 set cursor hotspot (two halfwords, then `lightPositionCursor`; the module's name for it is `SET_CURSOR_HOTSPOT`), 20002 pixel DMA (24 bytes, `Lg1PixelDma`; the module calls it `LG1_PIXELDMA`), 20003 set destination planes (`lightSetDestinationPlanes`: keeps bits 28:0 of the window's saved `AUX2` and ORs in the argument, stored to `AUX2` when the window owns the screen), 20004 set screen mask (four halfwords to `lightSetScreenmask`), 20005 get geometry (16 bytes out), 20006 read the colour maps, display modes and scan tables (0x10c82 bytes out, below), 20007 `AUX1` register update. The X server uses 20001 and 20002 and the general graphics-manager requests below. Other numbers print "lg1: unknown ioctl".
- **Read-back for request 20006 [binary].** `lightReadDisplay` (+0x1be0) fills 0xc00 bytes of colour map (four banks of 768, `light_read_bt_colormaps` +0x16bc or `light_read_lut_colormaps` +0x1770), one byte of VC1 register 0x62 (`light_read_auxmapindex` +0x1814), 0x40 display-mode halfwords (`light_read_displaymodes` +0x1864) and, from +0xc82, the decoded VC1 frame and line tables (`light_read_scan` +0x1924: for each of the 768 lines a record of line number, repeat count, entry count and that many halfwords, repeated lines folded into the previous record's count; the buffer is 0x10c82 bytes in all, so the scan part is variable and at most 0x10000 bytes). It also reads `CONFIGSEL` and VC1 registers, as the cursor code does. So the colour map, the VC1 register file, the XMAP table and the SRAM must be readable, not write-only; see the read protocol on the [REX1 page](../../devices/rex1/registers.md) (`RWVC1`, `RWDAC`) and [VC1](../../devices/vc1/README.md#readback-and-the-retrace-handler).

### Kernel: interrupts

- **Hooks [binary].** `lg1_init` (`light.o` +0x236c) allocates a 0x114-byte board structure per board (5.3; the 6.5 build uses 0x124 bytes), registers it with the graphics manager, sets bit 3 of the INT2 port register (0x1fb801df) with a bus flush, and installs two handlers through `setgiovector`: `lightRetrace` on GIO line 2 (INT2 local 1 bit 7) and `lightFIFO` on GIO line 0 (INT2 local 0 bit 0). The 5.3 build also installs a quad-board handler (`lightQuadRetrace` +0x2180, local vector 14) only for three or more boards; the 6.5 build has no such handler.
- **Retrace (`lightRetrace` +0x20cc) [binary].** Count the interrupt, run `lightRetraceHandler` for each board slot in the table, then acknowledge: clear and set bit 3 of 0x1fb801df with a flush between, which drops local 1 bit 7 (see the chips INT2 page). Nothing on the board is read or written to acknowledge. What on the board generates the pulse: unknown (no VC1 field names it); a model may raise it once per frame at the video rate it chooses when video is on.
- **What the retrace handler touches (`light_retrace.o` `lightRetraceHandler` +0x40) [binary].** It runs in interrupt context while a user process may be in the middle of VC1 accesses, so it saves and restores the VC1 selector and address counter: wait for `CONFIGMODE` bits 28:24 to be zero, read `CONFIGSEL` into a register, write `CONFIGSEL` 4 and read the address-low byte back through `RWVC1` (GO read, then read), write it back unchanged, `CONFIGSEL` 5 and read address-high. For each of the 32 swap slots with a request that is due (pending and with its frame count down to the last frame) it sets address 0, address 2n, `CONFIGSEL` 1, reads the two bytes of display-mode entry n (GO read then read, twice), clears or sets bit 1 of the second byte, and writes both back; then it restores address and selector. If the saved address-low byte is odd and the saved selector is 1 or 2 (a data window), it first reads VC1 register 0x0080 through window 0 and, at the end, steps the address back by one and writes the value read at that position through the saved window, then restores the selector. **[inferred]**: the odd-address case is a half-written two-byte entry, and the byte it re-stores is the chip's last-written data byte, which means register 0x80 reads as a data latch; a model whose register 0x80 reads 0 corrupts the table byte at the interrupted address. The same sequence is in `lightPositionCursor` (+0x548) and `lightReadDisplay`.
- **FIFO (`lightFIFO` +0x0) [binary].** Clear bit 0 of the INT2 local 0 mask (0x1fb801c7), then poll the local 0 status byte (0x1fb801c3) bit 0 for up to 300000 microseconds; count it; set the mask bit again. If the status bit never falls, print "lg1: REX fifo timeout." and scan the process table with signal number 9 in the argument block (**[inferred]**: it kills the processes that have the board mapped). A model with no FIFO interrupt never enters this handler. If the model raises it, the status bit must fall once the pending commands have drained.

### Kernel: window context switch

`lightPcxSwap` (`light.o` +0x1088) saves one window's drawing state and loads another's, only when two GL-style clients share the board. **[binary]**: after waiting for not busy it reads, one register at a time, `XSTART`, `YSTART`, `COLORRED`, `COLORGREEN`, `COLORBLUE`, `LSPATTERN`, `LSMODE`, `ZPATTERN`, `XSAVE`, `RWAUX1`, stores 0 to `TOGGLECTXT` (0x47f4), reads `XSTART`, `YSTART`, the three colours, `SLOPERED` to `SLOPEBLUE`, `XENDF`, `YENDF`, `AUX1`, `LSPATTERN`, `LSMODE`, `ZPATTERN`, `XSAVE`, `MINORSLOPE`, `XYMOVE`, `COLORBACK`, `AWEIGHT`, `RWAUX1`, `RWAUX2`, `RWMASK`, `COMMAND`, `SMASK1X`, `SMASK1Y`, then the four extra screen masks, `XYWIN`, `AUX2` and `CONFIGMODE`. It loads the incoming window with a GO no-op store at 0x800 after the coordinates, the same registers by plain stores, `TOGGLECTXT` again, and `CONFIGMODE` last. A flat register file that returns what was stored (including `XSTART`, `YSTART` and the colour registers as stored words) restores correctly. The X server alone never triggers it.

### X server: how it reaches the board

- **Opening [binary].** `irixKernInit` (Xsgi 0x100465ec, the server binary in the 5.3 `x_eoe` image) opens `/dev/opengl` (flags 0x802), issues request 103 (`GFX_ATTACH_BOARD`, structure: board number and the user address to map at, which the server computes as a base plus board number times the per-board size), opens `/dev/gfx`, and issues requests 1000 and 1002 (the server's messages call them rendering-node open and bind) and 111 (`GFX_LABEL`, which returns the board label). The loaded module then reads the board-info record and uses the mapped registers directly. The kernel side of 103 is `lightAttach` above. The module's own checks: it expects the board label to start "LG1MC" (name only), a matching dynamic-DDX version, and the inventory (`scaninvent`) to name the CPU board type for the FIFO level default.
- **Start (`rexInitHW`, `lg1mc.so` 0x5e2d2720) [binary].** Wait not busy; `XYWIN` 0x08000800; `CONFIGMODE` = 0xc0000000 | 0x00180000 | (level << 13) with level 7 by default (9 or 11 on some CPU board types when the board-info flags byte has bit 6 clear or set; override by the environment variable `REX_GFIFO_LEVEL`; `PRINT_GFIFO_LEVEL` prints it); `AUX2` 0x20000000; GO `COMMAND` 0; `AUX1` 0; `COMMAND` 0x329; `XSTATE` 0x03ff0000; `AUX2` 0x60000000 and a full-screen clear; `AUX2` 0x20000000 again and a second clear. The first clear uses both plane groups (bits 30 and 29) and the second the displayed one, so the model must treat the `AUX2` top bits as independent group selects: 0x20000000 is the displayed group, 0x40000000 a second group the PROM and the kernel also clear, 0x60000000 both. Reads: only `CONFIGMODE`.

- **Logic operations and write mask.** The X raster operation (0 to 15) is passed in `XSTATE` bits 31:24 (rect, point, copy paths) or in `COMMAND` bits 31:28 (host-data writes and glyph paths), so every one of the sixteen operations can be issued, not only replace (3). The write mask is `XSTATE` bits 23:16; `RWMASK` is not touched by the X server. [inferred] The model needs source and destination logic for all sixteen operations on 8-bit pixels and a plane mask; the PROM and kernel use only replace with mask 0xff.
- **Plane groups.** `AUX2` bits 31:29 pick the target group(s) for every command (`group << 29`, group 1, 2 or 3). One group is displayed; the second is used for overlay and window-id fills (`rexClearOverlays` writes 0x40000000, the id fill 0x60000000); how an 8-bit-per-pixel LG1 shows a second group, or whether it only exists as scratch storage: unknown. A model that discards writes whose group does not include 0x20000000 draws the same screen as one that keeps two planes.
- **Copy direction.** `rexCopyRect` loads `XSTARTI` = x0 and `XENDI` = x1 - 1 when dx is not negative and `XSTARTI` = x1 - 1 and `XENDI` = x0 when it is (with dx negative and x0 below 4 it loads `XENDI` four higher and shifts `XYWIN`, see [REX1](../../devices/rex1/registers.md)), and the same for y with dy. So the engine must run from the start register toward the end register in either direction, reading the source at start plus the `XYMOVE` offset.
- **XYMOVE sign (question settled).** dx is source minus destination x, dy source minus destination y, both in stored coordinates, with the source read at destination plus `XYMOVE` ([binary] arithmetic; the pairing "destination is the rectangle" **[inferred]** from the direction logic, which is only correct if so). Agrees with NetBSD. Only the PROM copy routine, with no caller found, is unchecked.
- **Host-data pixel transfers.** A write stores 32-bit words at `RWAUX1` GO, one word per four pixels with the first pixel in the high byte; the source is re-aligned in software (shift and merge of two source words, `rexDrawImage` 0x5e30f9a8 to 0x5e30fa34) and the handling of a first word that starts mid-word (the module adjusts `XSTARTI` and, below x = 4, `XYWIN`) was not decoded: open. Rows end at `XENDI` without a `STOPONX` flag. Reads from `RWAUX1` GO return four pixels per word. A PutImage of 16384 pixels or more uses request 20002 (0x4e22) instead whenever the flags byte (record +0x30, which always has bit 7 set on the IP20) is 2 or more: the kernel then programs the MC graphics DMA with `CONFIGMODE` 0x807fe000 held and restored afterwards (`Lg1PixelDma`, `light_dma.o` +0x728; the MC call and its GIO address are decoded in the review below). If request 20002 fails the module prints "lg1DrawImage: LG1_PIXELDMA failed" and carries on without redrawing that rectangle, so a model without the DMA loses large images (image viewers, root-window pictures); small ones go through `RWAUX1` as above.

### X server: the colour map, VC1 and cursor

- **Colour map [binary].** `bt479Init` (0x5e31b308) and `lutInit` (0x5e2d2bb0) load the table the kernel loads; `rexSetColor` (0x5e31951c), `rexStoreNormalColors`, `rexInstallNormalMap`, `rexStorePupColors` write palette entries by index in banks (four hardware maps, `rexNumHWCmaps`), each after a wait for `CONFIGMODE` bit 0 clear. On the LUT1 path `rexSetColor` reads the colour-map command register (`CONFIGSEL` 6, GO read, then `RWDAC` read), writes its low nibble back to select the bank, loads the entries, and restores the saved value. `rexBlankScreen` (0x5e3198c8) reads that command register and clears or sets bit 1 (LUT1) or writes the pixel mask 0 or 0xff through `CONFIGSEL` 2 (Bt479). Reads of the register file the module relies on beyond `CONFIGMODE`: the colour-map command register, `RWAUX1` GO, and a dummy `RWVC1` read at the end of `vc1LoadSRAM`.
- **VC1 [binary].** The module reinitialises the VC1 itself with a different register set and table layout from the kernel's (`vc1Init` 0x5e2d2d90, `vc1LoadSRAM` 0x5e3192f4, `vc1LoadDIDTable` 0x5e318954): it loads a frame table of 0x600 bytes at SRAM 0x900 and 16 bytes at SRAM 0x2000, writes VC1 registers 0x40/0x41 = 0x09 0x00, 0x42/0x43 = 0x0f 0x00, 0x44/0x45 = 0xcd 0x00, 0x60 to 0x63 = 0x01 0x01 0x31 0x00 (the kernel's `initVC1` wrote 0x40 to 0x45 as 0x40 0x00, 0x46 0x00, 0xcc 0x04 and 0x60/0x61 as 0x01 0x01), fills the first 32 display-mode entries with 0x0300 and rebuilds the per-scanline window-id (DID) line table in SRAM from the window clip lists, 16-bit entries with a run-length form (bit 15 set, count in the low 15 bits, as `light_read_scan` decodes). Display modes per window id then go to the kernel by request 1017 (**[inferred]** that it ends in `lightSetDisplayMode`, the only routine that writes the XMAP table): the 16-bit value is (old & 0x7003) | 0x300 | colour-map group bits, with bit 1 for the buffer (`rexChangeDIDCmap` 0x5e312a68). A model that stores and reads back the SRAM, the XMAP table and the register file satisfies every access; **what the VC1 does with them to choose the colour-map bank and buffer per pixel is unknown** (see [questions](../../questions/README.md)) and is needed to show an X session with more than one installed colour map correctly.
- **Cursor [binary].** `rexCursorInit` (0x5e2d3688), `rexInstallCursor` (0x5e308c4c), `rexDisplayCursor` (0x5e3082b8), `rexCursorOn` (0x5e319800): VC1 SRAM 0x3000 (256 bytes, two bits per pixel by the size) written through window 2, VC1 register 0x26 (0xc8 or 0xcb), the three cursor colours at colour-map addresses 0x21, 0x22 and 0x23 (`RWDAC` addresses with the command register at 0x82 saved and restored), and `SYS_CTL` bits 5:4 (`0x30`) for visibility, held in a software copy and written without read-back. Position and hotspot go through request 20001 and `lightPositionCursor` (x + 0x8c, y + 0x27 minus the hotspot, into VC1 registers 0x22 and 0x24).
- **Video board.** The `sv1*` and `Xvsv1*` functions drive an optional video input board through `/dev/video`; not part of the base model.

### What the model needs beyond the PROM

Addresses are the functions above.

1. **Readable state, not write-only.** `CONFIGSEL` (0x47ec), the VC1 address counter through `CONFIGSEL` 4 and 5, VC1 registers 0x40, 0x41, 0x62 and 0x80, the XMAP table, the SRAM, the colour-map command register and the palette (reads of GO after one discarded GO read), all coordinate, colour, slope and pattern registers, `COMMAND` and the four extra screen masks (`lightPcxSwap`, `lightReadDisplay`, `lightRetraceHandler`, `lightPositionCursor`).
2. **A one-deep read pipeline on the GO aliases** of `RWVC1` and `RWDAC` (see [REX1](../../devices/rex1/registers.md)).
3. **User-mode access** to the whole 0x5000-byte window.
4. **`WCLOCK` revision below 2 and `CONFIGMODE` bits 7:4 zero** (so `lightInitInfo` runs the pixel-memory probe) are already in the list above; additionally the MC graphics DMA must complete and raise INT2 local 0 bit 4 (CPU Cause bit 10) for the kernel's self-test, or the kernel flags the board as prototype hardware and the X server switches its FIFO level and DMA paths on that flag.
5. **Retrace interrupt** on GIO line 2 (INT2 local 1 bit 7), re-armed by the port register bit 3 pulse; **FIFO interrupt** on line 0 optional.
6. **`XSTATE`** as a packed colour, mask and operation word with the colour shared with `COLORREDI`; commands 0x329, 0x80329, 0x1, 0x121, 0x921, 0x200121, 0x2000a9, 0x2000ab, 0x5a1 to 0x5b9, 0x30000329 and 0x300005b9 (lines OR the operation and DRAW into 0x121 and 0x329 and write 0xf11 into the low bits of `AUX2`); all sixteen logic operations; the write mask; `AUX2` group bits; start and end registers in either order; `XYMOVE` as above; `XYWIN` as a coordinate offset.
7. **Host data** through `RWAUX1` GO in both directions, four pixels per word, high byte first.
8. **A per-pixel display-mode lookup** (window id from the VC1 tables, then mode, then colour-map bank and buffer) if X is to show more than one colour map; a model may start with bank 0 only and say so.
9. **`CONFIGMODE`** accepting the X server's words (gfifo level bits 17:13, constants in bits 20:19, 30 and 31) and returning small counts or zero in bits 12:8 and 28:24.

Still open, filed in [questions](../../questions/README.md): the VC1 DID and display-mode tables, what `XSTATE` bit 29 of the copy word selects, what the low bits of `AUX2` (0xf11 in line batches) do, and whether the second plane group is visible.

## Review (2026-11-23)

Independent review against `lg1.a`, the 4.0.5D and 4.0.5G PROMs, the IP20 `ide` image and the Library photograph; the register-level verdicts are in the
[REX1 review](../../devices/rex1/README.md#review-2026-11-23). Board-level results:

- **Probe, board order, revision rule (CONFIRMED).** The probe table at 0xbfc4d1f0 holds 0xbf3f0000, 0xbf3f8000, 0. `lightInit` chooses `initBt479` for revision below 2 and
  `initLUT1` otherwise, then `initVC1` only if the VC1 revision byte is above 0. Init order in the kernel: `initRex`, `rexClear`, `lightInitInfo`, `rexClear`, `initClock`, colour map, VC1.
- **Chip markings (GRADE kept: observed).** The photograph reads `L1A6654 VC1 REV B` and `L1A6651 LUT1 REV A`, board `030-8077-004 REV A`: correct. The REX package, which the first
  version called illegible, reads `LSI LOGIC`, a part-number line (L1A67x1, digits uncertain), `REX1.5`, `REV. A` (observed). The "Bt" package beside the LUT1 is observed but its
  part type is not legible; its presence on a board that also carries the LUT1 means the photograph alone cannot say which variant a given revision uses.
- **PROM console font and geometry (new, partly settled).** The PROM builds four font records at RAM 0xa8745720 (builder at 0xbfc318a8), 12 bytes each: bitmap pointer, glyph table
  pointer, then two halfwords (cell height and descent). Glyph records are 8 bytes: halfword offset into the bitmap in halfwords, width, height, signed x and y origin
  (negated before use), halfword advance. Bitmap rows are padded to 16 bits. Font 0: bitmap 0xbfc542c0, table 0xbfc5535c, 17 and 4, 9 pixel advance, 190 glyph records
  (index = code - 32, or code - 66 when bit 7 of the code is set). Font 2: 0xbfc559dc, table 0xbfc5693c, 23 and 5, 19 pixel
  advance. Font 3: 0xbfc56c34, table 0xbfc57358, 14 and 3, 9 pixel advance, 9x11 'A'. Codes below 7 select font 1 (a 7-glyph set of box-drawing pieces at table 0xbfc559a4, bitmap 0xbfc5594c).
  The character draw routine is 0xbfc41a14; it fills the descriptor and calls the board's draw-bitmap entry (table entry 6). The PROM's console repaint loop (0xbfc30154) advances 9 pixels per
  character and uses font 0. The window setup function (0xbfc2f864, called with 18178 or 18181) sets cell 9 by 17 and 80 columns, with 36 rows when the screen height is 768
  and 40 otherwise; for 18181 it first runs the 18179 variant (cell height 20, 10 wide, 20 rows). The 4.0.5D data word at 0xbfc42e20 that picks between them is 1, which selects the 18181 chain;
  The font bitmaps themselves were decoded (the 'A' and 'g' glyphs render correctly).
- **Console geometry (settled 2026-11-23).** The word at 0xbfc42e20 is a constant in the ROM image, not RAM (4.0.5G: 0xbfc45f40, also 1). The console
  initialiser (0xbfc31978 in 4.0.5D, 0xbfc2c71c in 4.0.5G) reads it: nonzero calls the window setup with 18181, zero with 18178. The word is 1 in
  both images, so every shipped LG1 console takes 18181, which first runs 18179 and then ORs 7 into the window flags. The 18179 variant sets line pitch 20, descent 6, 80 columns and
  a fixed 20 rows (the screen height is not consulted); its advance field is 10, which no drawing code read here uses. Text is still drawn with font 0 (cell height 17, descent 4, glyph advance 9), and the window width is 9 times the columns, so the grid is 80 columns of 9 pixels (720) by 20 rows of 20 pixels (400). The frame drawn around it spans the window origin minus 2 to plus
  9 x columns + 5 and plus line pitch x rows + 5, which is an outer 728 by 408 and an interior of 726 by 406 with the one pixel border: the emulator session's measurement agrees exactly.
  The 80 by 36 (or 40) window with 9 by 17 cells is the 18178 variant, reached only if that word is zero or the code unknown: not taken by either shipped PROM. Grade: established for the
  selection, inferred for the unused advance field. The 1024 by 768 LG1 console is therefore 80 by 20 in 9 by 20 cells.
- **Y of the console.** The PROM's console y counts up from the bottom (first text row at the largest y) and stored y is 767 minus it, so stored y is the row from the top;
  evidence and grade in the [REX1 page](../../devices/rex1/README.md#y-origin).
- **What the PROM relies on for visible output.** Reads: initRex-equivalent stores `XYWIN` 0x08000800, `CONFIGMODE` 0x807fe000, `AUX2` 0x20000000, a no-op at the command GO alias and `AUX1` 0 (0xbfc0fd58-0xbfc0fda8), and the
  board-info routine stores `RWMASK` 0xff (0xbfc0fa94); nothing else in the LG1 init or console path (0xbfc0f000-0xbfc10400, 0xbfc2d430-0xbfc2dab0, 0xbfc2f864-0xbfc31a40) writes the screen masks,
  `XYWIN` or the write mask again, and no drawing command in the PROM sets a clip or write-mask flag. A model may store `XYWIN`, the four extra screen masks, `SMASK1X/Y` and `RWMASK` without effect on
  the PROM console, provided drawing reaches the single displayed 8 bpp plane group (the PROM leaves `AUX2` at 0x20000000, the group the kernel clear also hits second) and `XYWIN` = 0x08000800 means no offset (inferred; any other value is unknown).
  Grade: established for the store list, inferred for the "no effect needed" conclusion (an emulator run shows model behaviour only).
